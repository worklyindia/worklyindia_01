- Keep _shared/jobPayments.ts prices identical to the website calculation (latest active settings row), so charged amount matches shown price.
- Customer WhatsApp events are forwarded from meta-whatsapp-webhook to the owner's webhook_endpoints via _shared/customerWebhooks.ts, signed with the endpoint secret.
- Public Email API: wfh_ keys (x-api-key) are routed inside unified-notifications-api to _shared/emailPublicApi.ts, which uses the key owner's own AI Connect mailbox (Gmail/Outlook/domain) and returns 409 mailbox_not_connected with no platform fallback, so senders are always the developer's own address while usage stays metered. Each user's new inbox mail reaches their own webhooks as email.received via the /email-api-poll cron, because there is no shared push channel across Gmail/Outlook/IMAP.
- API Auto-Top-Up auto-debit lives in create-api-subscription (actions topup_mandate_order/verify/cancel/topup_check): users authorize a Razorpay order token once (first top-up charged then), and _shared/apiQuota.ts fire-and-forget invokes topup_check with the service-role x-topup-secret header when remaining < 10000; mandate columns in api_auto_topup_settings are server-only (column-level GRANT), because users must not self-mark a mandate active.
- Razorpay invoices: one per payment_id via _shared/razorpayInvoice.ts, downloaded through the hosted short_url, because Razorpay has no PDF API.
- Razorpay customers: _shared/razorpayCustomer.ts creates one customer per user+mode (claim row first, fail_existing=0, retries 5xx/429) and links every order in razorpay_customer_payments; final payment status is written only by razorpay-webhook, because frontend success is not proof of payment.
- Public WhatsApp API: wfh_ keys (x-api-key) are routed inside whatsapp-embedded-signup to _shared/whatsappPublicApi.ts using the key owner's company number; a separate function was not deployable (function-count cap).
- Developer sub-accounts (_shared/whatsappSubAccounts.ts): a wfh_ key owner's own users connect WhatsApp through one-time hashed connect links (scope sub_connect in workly-india) and their numbers/tokens live in developer_sub_account_* tables, never in employer_whatsapp_*, so a developer's users can't leak into employer screens and every lookup stays scoped to the key owner.
- Developer sub-account Instagram/Facebook/Gmail/Outlook/domain mailboxes are stored in social_meta_accounts / app_user_connections with the sub-account id as owner id (_shared/subAccountChannels.ts), so existing send/read code is reused while rows never match any signed-in user; every lookup goes through findSubAccount scoped to the key owner.
- WhatsApp tier and quality: Meta is the only authority, so _shared/whatsappTierSync.ts re-reads whatsapp_business_manager_messaging_limit (the portfolio limit WhatsApp Manager shows; the old messaging_limit_tier is deprecated and stays stale at TIER_250) and quality_rating live from Meta whenever the limits overview or a profile screen is opened and writes them back, and the send path prefers that live value over the stored column — because the stored copy only moves on a Meta webhook, and a missed push must never let the website show or enforce a limit Meta no longer honors (or hide one it granted).
- WhatsApp Meta block: _shared/whatsappTierSync.ts also reads Meta's phone `status` and stores meta_status/meta_blocked; consumeWhatsappSend refuses every send for a blocked number and the flag clears automatically when Meta reports it usable, because the website must never send through a number Meta blocked. The daily refresh runs as workly-india scope tier_refresh (no separate function, function-count cap).
- Instagram/Facebook reply_to, reactions and inbound attachments are recorded from webhooks into social_meta_message_events (server-only) and merged in chat_messages, because Meta's Conversations API does not return them reliably.
- _shared/chatWidget.ts: legacy visitor actions return 410; each developer has one widget ID (developer_chat_widgets, server-only) and a hashed 6-digit PIN, and only a correct PIN (5 tries, then 15-min lock) mints a sign-in for that developer, because embed code itself must never grant inbox access. Widget access (Chat and Email share one PIN) is gated only by an active, unexpired api_subscriptions row; widget use never deducts API calls.
- QR Code / Payment Request (create-api-subscription qr_*/link_*) accept any website order the user owns (notes.user_id or notes.ref): Developer products are credited server-side, other products return server-signed order|payment params so each page's own verify step credits them.
- Supabase Auth Send SMS hook lives at whatsapp-cloud-api/sms-hook (Standard Webhooks, SEND_SMS_HOOK_SECRET) and delivers phone OTPs via the job seeker or employer WhatsApp number by user_metadata.user_type, because SMS delivery is replaced by WhatsApp.
- Email sender resolves preview artwork through emailImageAssets into immutable public brand-assets copies; restrict fetches to known asset hosts so Gmail does not depend on preview access or expose internal URLs.
- PayPal webhook lives at paypal-webhook (URL https://jubwzelupbntbetpajqb.supabase.co/functions/v1/paypal-webhook); it reads PAYPAL_CLIENT_ID/SECRET/WEBHOOK_ID/MODE from the Owner Secrets page first with edge env as fallback, verifies signatures via PayPal verify-webhook-signature, and dedupes events in payment_events (server-only).
- PayPal owner wallet/refund run inside paypal-webhook (requests without paypal-transmission-id, owner-only): wallet = captures/sales minus refunds, reversals and payouts from verified payment_events, deduped per resource id, because the website must show the PayPal balance without opening PayPal.
- PayPal payments live in paypal_payments (row created by create-api-subscription paypal_create, user read-only via RLS); status and refunds are written only by verified paypal-webhook events and merged into employee-payment-history, because client polling is not proof of payment or refund.
- Lifecycle WhatsApp (4th fan-out channel) lives in _shared/lifecycleWhatsApp.ts: sends the approved template named <event>_<audience> from that audience's own number, gated by whatsapp_templates.notify_enabled (owner switch), because job seeker and employer numbers must never cross.
- Login Turnstile keys live in Owner Secrets and are served via unified-2fa (turnstile-config/turnstile-verify); the client hides and skips Turnstile on hosts outside the owner's Domain Settings canonical domain (src/lib/turnstileDomain), because Cloudflare rejects unlisted hostnames and the function cap blocks a new function.
